# AarogyaTwin-X Day-1 explanation

## What was built today

We built a small, local research prototype called **AarogyaTwin-X**. It uses completely artificial patient data to demonstrate how a glucose forecasting system could work.

### 1. What the data is

The system creates **60 synthetic patients**. Each patient has:

- Age, sex, BMI, HbA1c, diabetes duration, and medication labels
- Glucose readings every 5 minutes
- Heart rate
- Heart-rate variability
- Sleep information
- Activity/steps
- Meal carbohydrate amounts

Each synthetic patient has **5 days of data**.

The data is generated by a simulator. It is not collected from real people, and simulator settings are not treated as real physiological measurements.

The simulator also creates realistic problems such as:

- Missing CGM readings
- Short gaps in heart-rate data
- Different meal and activity patterns
- Different glucose responses between patients

### 2. What the model does

At a selected point in a patient’s timeline, the model looks only at information that would already be available at that time.

It produces:

1. A glucose estimate for **30 minutes ahead**
2. A glucose estimate for **60 minutes ahead**
3. A glucose estimate for **120 minutes ahead**
4. An uncertainty interval around each estimate
5. An estimate of whether a new sustained high-glucose event may occur within 120 minutes

The event definition used for this prototype is:

- Glucose must be strictly above `180 mg/dL`
- It must remain above that level for four consecutive 5-minute readings
- The existing glucose level cannot already be above the threshold if we are estimating a *new* event

The model uses:

- A CPU-friendly regression model for future glucose
- A logistic classifier for the event estimate
- Recent glucose history, glucose trend, heart rate, HRV, activity, sleep, meals, and static patient information

Missing numeric values are filled using statistics learned from the training patients. Missingness indicators are also given to the model so it knows that a value was unavailable.

If recent CGM data becomes too old or too incomplete, the system **does not guess**. It marks the prediction as unavailable and explains why.

### 3. How it was evaluated

The synthetic patients were divided into separate groups:

- 36 patients for training
- 12 patients for calibration
- 12 patients held out for testing

The same patient never appears in both training and testing. This is important because otherwise the model could memorize a patient’s behavior and appear better than it really is.

The model was tested on the held-out patients.

For glucose forecasting, we measured:

- Average absolute error
- Root-mean-square error
- How often the uncertainty interval contained the real future value

Measured synthetic results:

| Horizon | Average error | Interval coverage |
|---|---:|---:|
| 30 minutes | 7.21 mg/dL | 89.47% |
| 60 minutes | 7.91 mg/dL | 89.87% |
| 120 minutes | 8.66 mg/dL | 89.64% |

The target interval coverage was 90%.

For the high-glucose event classifier, we measured:

- AUROC: `0.943`
- AUPRC: `0.277`
- Brier score: `0.050`

These numbers describe performance on this particular simulator. They are **not clinical accuracy results** and do not show that the system works for real patients.

We also compare the model against a simple baseline that predicts future glucose using the last observed glucose value. The learned model performed better than that baseline on this synthetic test set.

### 4. What the dashboard shows

The dashboard lets someone:

- Choose a held-out synthetic patient
- Move through the patient’s timeline
- Advance the replay clock by 5 minutes
- View recent observed glucose history
- See current glucose, heart rate, activity, sleep, and glucose trend
- See the 30-, 60-, and 120-minute forecast points
- See uncertainty intervals
- See the estimated 120-minute event risk when it is valid
- Turn on a simulated 30-minute CGM dropout
- See warnings when the data is too stale or incomplete
- View measured evaluation metrics
- View model and data provenance
- Compare an assumption-based activity/meal scenario with the normal forecast

The dashboard labels context signals as **observed context**, not causal explanations. It also clearly states that the scenario tool is not a treatment estimate and must not be used for medication or dosing decisions.

In short:

> The system generates an artificial patient timeline, learns from past observations, forecasts several future glucose points, refuses to guess when data quality is poor, and presents the result with uncertainty and limitations in a local dashboard.
